# Operator GPU Viewer Shutdown Qualification

## Scope and ownership

This qualification concerns only the productive WPF `ProgramViewer` GPU
presentation fixture, its bounded monitoring-reader lifetime and the
test-owned in-process `ControlHostProcess` / `RuntimeHostProcess` lifecycle.
The viewer has **observation-only** authority. Neither host, Program clock,
native decoder, output provider, recording transport nor persisted production
schema changes as part of this qualification.

Source baseline: `master`
`f22345f802c2c8c3515a0cc4ad068618d9d8798f`. Confirm that the
starting `master` remains current when executing a new iteration.
The SDK pin is `global.json` (`10.0.401` at this baseline).
Version changes are governed by `docs/Versioning.md`; test-only refinements
do not increase the tracked product patch version.

## Deterministic fixture teardown

`MonitorPresentationQualification` owns an isolated child xUnit test
process. Within the child, ControlHost and RuntimeHost are **in-process
fixture-owned services**; they are not adopted service processes or
externally supervised production hosts. The parent captures both output
streams, child PID, completion/exit result and bounded timeout. The child
owns its STA dispatcher and WPF `OperatorResourceApplication`.

On both successful viewer execution and viewer exceptions, the child
now executes **separately logged, non-skipping teardown phases**:

1. Cancel the bounded Program monitoring stream; await its enumerator
   disposal before host cancellation, then dispose its token.
2. Clear the viewer GPU/frame references, detach the viewer, close the
   owning WPF window and yield through Dispatcher Loaded. Confirm
   `Unloaded`, null native color/view resources, zero rendering
   subscriptions and `TargetCreateCount == TargetReleaseCount`.
3. Cancel and await the fixture-owned ControlHost. Assert its **actual**
   `ControlHostExitCode.Success` and `Stopped` lifecycle, including
   the full `Lifecycle.Detail` and structured `ShutdownPhases` in
   the diagnostic trace.
4. Cancel and await the fixture-owned RuntimeHost and assert
   `RuntimeHostExitCode.Success` and `Stopped` lifecycle.
5. Remove the temporary durability root only after both host tasks
   complete; retain it when a host remains running.
6. Combine any independent visual/monitor/host/cleanup exceptions into
   a failing test result. Only after **every** check passes may the
   child emit `VIEWER SHUTDOWN PASS` and `VIEWER PROGRAM PASS`.

The fixture uses bounded **observer** waits for host completion; it does
not increase either host's configured shutdown timeout, change production
retries, suppress exceptions or accept non-success exit codes.

### How to attribute failures

- `VIEWER VISUAL FAIL`: WPF, texture, DPI, transport presentation or
  expected viewer behavior failed before teardown. This is independent
  of any later host cleanup failure.
- `VIEWER TEARDOWN FAIL phase=monitor-*`: stream cancellation or
  disposal failed. Check the bounded reader owner and named-pipe state.
- `phase=viewer-unload`: real WPF/COM, target count or Dispatcher
  ownership failure. Check rendering subscription, image and texture
  lifetimes before any host changes.
- `phase=control-stop`: exact `ControlHostExitCode`, lifecycle detail
  and each recorded shutdown phase isolate binding-worker, IPC,
  runtime transport or durability drain. Do not label it GPU failure
  without a matching surface exception.
- `phase=runtime-stop`: actual RuntimeHost exit/lifecycle details
  separate a Runtime drain failure from viewer teardown.
- `phase=durability-root-cleanup`: cleanup-only failure after the
  services have returned; this never turns either service's bad exit
  into a pass.

## GPU/DPI regression

The original productive Program observations still come from the
existing named-pipe RuntimeHost monitoring stream; the red GPU texture,
readback and epoch/adaptor rejection cases are explicitly **synthetic
interop verification**. The existing Model zoom test covers 100 zoom-in/
out cycles at each of four scales, with an exact origin check.

The real WPF GPU surface tests additionally cover target creation and
retirement, minimize/restore, hide/show, unload/reload, simulated
front-buffer loss and deliberate device removal followed by bounded
recovery. The DPI fixture holds the same target stable across 100
invalidate/dispatcher cycles at each 100%, 125%, 150%, 200% injected
scale; it reports **P99 of real Windows WPF Dispatcher Loaded
completions** for 400 cycles, not GPU frame latency. The test also
asserts the last target/COM release and zero active rendering
subscriptions after closing. Pixel readback is performed against a
real D3D11 surface on the runner, but Basic Render Driver results
are **not** physical NVIDIA/CUDA, reference SSD or external video
output acceptance.


Repeat the isolated child test with several fresh worker processes and
vary filter execution order before attributing a sporadic fault. Capture
full PID/phase/exit/recovery logs, source SHA, runner OS/graphics adapter,
pinned SDK and exact test name. Source code changes alone do **not**
constitute a passing GPU or host-lifetime qualification.

On the **final PR HEAD**, assess `CI`, `Quality`, `Security`,
`Provider Smoke` and `Packaged E2E` independently with job/step
status and required artifacts. In-progress, missing, failed, cancelled
or skipped is **not PASS**. No unrelated unit/Runtime/recording changes
are authorized by a failure in another team's exclusive code surface.
